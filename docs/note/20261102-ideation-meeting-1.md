## 논의만 하고 정하지 않은 것

### 심사 기준 추정

- 코드 레벨보다 아키텍처·안정적 배포·운영 지속 가능성, AI 활용 가이드라인을 잘 잡아 빠르게 만들었는지가 볼 것 같다는 추정 (참석자 1·2). **공식 기준 아님**.
- 카나리·블루그린 배포 같은 인프라 파이프라인은 시간이 남으면. 처음부터 넣지는 않는다는 쪽으로 기울었음.

### LLM: 클라우드 API vs 로컬 모델

- 참석자 2: 공공기관 연계 서비스라 개인정보를 클라우드 API로 보내는 건 위험, 로컬 LLM(회사 GPU 서버 사용 허락 받음)이 가산점일 수 있다.
- 참석자 1: 클라우드와 오픈소스 모델의 성능 격차·구축 비용·마이그레이션 부담. 다루는 데이터가 정해지기 전이라 지금 정할 단계가 아니다. "실서비스 때 로컬로 바꾼다"로 설명 가능.
- 참석자 3: 로컬이 빅테크 클라우드보다 안전하다는 보장이 있나.
- → 아이디어·데이터가 정해진 뒤 재논의.

### OCR

- 상용 OCR 무료 할당량 + LLM 구조화 (참석자 1), Upstage OCR을 지인 통해 받을 수 있을 것 (참석자 2).

### 배포

- Vercel 단순 배포는 아쉽다 (참석자 2) vs 도메인 하나 사서 배포하면 충분, 아이디어가 제일 중요 (참석자 1).
- 보유 중인 미사용 도메인 있음 — 서비스명과 맞지 않으면 의미 없음. 자동 갱신 해지 필요 (참석자 2 개인 할 일).

### 팀 구성

- 현재 4명 + 백엔드 1명 참여 예정. 역할 후보: 프론트 2, 백엔드 1, 프롬프트·LLM 엔지니어링 1, 기획·디자인은 공동.
- 디자이너는 디지털 격차를 줄이는 데 중요하지만 별도 인원 없이 다 같이 챙긴다.
- 신청서의 "주요 역할" 문항이 팀 밸런스 확인용이라 포지션을 나눠 적어야 할 수 있음. 인원 추가 여부는 수요일까지.
- 참가 신청이 모두 선발되지는 않을 수 있음.

### 회의 중 언급된 주최측 정보 (원문 확인 필요)

- 6시간 당일형 해커톤, 사전 바이브 코딩 세미나(AI 코딩 도구로 웹 서비스 만들고 배포하기).
- 후원: 과학기술정보통신부, 서울AI재단, NIA, 서울특별시. 운영: 구름.
- 신청서: 아이디어 500자 이내, 팀원별 포지션(기획·프론트·백엔드 등 단일 선택), 기술 숙련도 자가평가.
- 해커톤까지 약 3주.

## 아이디어를 낼 때 관점 (회의에서 나온 것)

- AI를 어디에 쓰는지가 분명해야 한다. 깊이보다 활용 지점이 명확한 것.
- 개인에게만 이득인 서비스보다 공동에게 이득인 구조 — 모두가 쓰면 효과가 사라지는 해결책은 방어가 약하다.
- "왜 이게 근본 원인인가" 질문에 답할 근거를 준비한다.
- 공무원용 업무 도구에 매몰되지 말고 시민이 쓰는 서비스로.
- 정보 약자(장애인·고령자)가 타자를 칠 수 있는가 — 화면 대신 말로 하는 인터페이스도 후보.
